# T-15 — замер служебного оверхеда `claude -p`

Замерено на машине исполнителя тикета: Windows, `claude` CLI 2.1.245, модель
`claude-haiku-4-5-20251001`, тривиальный запрос («Ответь одним словом: да» +
короткий системный промпт «Ты - тестовый ассистент.»). Метрика — сумма
`usage.input_tokens + usage.cache_creation_input_tokens + usage.cache_read_input_tokens`
из элемента `type == "result"` (см. `ergovault/llm/cli_backend.py`).

| Конфигурация | Команда (добавочные флаги) | Служебный оверхед, токены |
|---|---|---:|
| 1. Без флагов минимизации | `claude -p <user> --output-format json --model <model>` | **37 741** |
| 2. + системный промпт и статичные настройки | `+ --system-prompt <system> --exclude-dynamic-system-prompt-sections --setting-sources ""` | **26 691** |
| 3. + отключение slash-команд и инструментов | `+ --disable-slash-commands --strict-mcp-config --disallowedTools Bash Read Write Edit Glob Grep WebSearch WebFetch Task NotebookEdit Artifact Skill ToolSearch` | **16 824** |

Полные JSON-ответы всех трёх прогонов сохранены при замере (не прикладываются к
репозиторию — содержат список инструментов и session_id текущей машины).

## Соответствие цифрам из тикета

Тикет T-15 приводит ориентировочные цифры «34 206 → 26 577 → 16 819» (тоже Haiku 4.5,
тривиальный запрос). Мой независимый прогон на своей машине даёт тот же порядок и ту
же нижнюю границу:

- конфигурация 3 (все флаги минимизации) сходится почти точно: 16 824 против 16 819;
- конфигурация 2 сходится почти точно: 26 691 против 26 577;
- конфигурация 1 отличается заметнее (37 741 против 34 206) — по всей видимости из-за
  разницы в списке доступных инструментов/MCP-серверов текущей сессии, которые без
  флагов минимизации целиком попадают в служебный контекст; сама точка (~34–38k без
  флагов) не меняет вывод тикета.

Вывод тикета подтверждён: минимизирующие флаги снижают оверхед примерно вдвое
(с ~34–38k до ~17k), ниже ~17k подтверждённо не опускается — это базовый системный
промпт Claude Code и определения оставшихся инструментов.

## Замечание к стоимости

`total_cost_usd`, который сообщает cli в элементе `result`, посчитан по всем токенам
запроса, включая служебный оверхед и кэш-запись/чтение по своим ставкам — это не то
же самое, что `billed_cost_usd` в `ergovault/llm/pricing.py`, который считает по
собственному прайсу от `usage.input_tokens`/`usage.output_tokens`/кэша. На прогоне
конфигурации 3: `total_cost_usd = 0.0043889`, `billed_cost_usd` (та же usage,
прайс Haiku 4.5) = 0.00288565 — величины закономерно не совпадают, тест на это есть
в `backend/tests/test_llm.py::test_billed_cost_usd_not_equal_to_raw_cost_usd`
(на данных зафиксированной фикстуры, не на живом вызове).
