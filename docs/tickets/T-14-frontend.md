# T-14 — Фронтенд: три экрана на моках контракта

**Пакет:** `frontend/` — только он.
**Читать перед стартом:** `docs/CONTRACTS.md` §7–8, спека проекта раздел 3 (макет экрана).
**Зависит от:** T-00 (контракт типов). API ещё нет — работаем на моках, это не блокер.

## Задача

React + TypeScript + Vite. Три экрана из спеки, полностью на моках `msw`, с типами,
сгенерированными из контракта §7–8. Когда T-22 поднимет API, переключение — сменой базового URL.

## Экраны

1. **Вопросы по исследованию** — поле вопроса, примеры запросов, ответ, блок «На чём основан
   ответ», блок «Ограничения», кнопки `Полезно` / `Есть ошибка`.
2. **Библиотека** — таблица источников: тема, язык, дата, тип, `speaker_org`, `stance`,
   пометка `derived`, `reliability_note`.
3. **Проверка качества** — заглушка под `GET /api/eval/summary`: набор вопросов, результаты,
разобранные примеры. Наполнит T-31.

## Обязательные требования к отображению

- Ссылка `[n]` в ответе кликабельна и раскрывает **конкретный фрагмент**: заголовок раздела
  (`heading_path`) + дословная цитата + ссылка на оригинал. Не название большого документа.
- Блок «Ограничения» рендерится из `limitations`, каждый вид — своя формулировка и иконка.
  Ограничения приходят с бэкенда готовыми; фронт их не сочиняет и не переписывает.
- **Процент уверенности не показывать никогда** — ни в каком виде. Требование спеки.
- Состояние `refused: true` — отдельный, спокойный вид: чего именно не хватает в материалах.
  Это витрина проекта, а не ошибка; оформить как полноценный ответ, а не как пустой экран.
- `url: null` — показывать источник без ссылки, не подставлять заглушку и не прятать источник.

## Что сделать

1. Vite + TS + минимальный набор зависимостей. Роутер, fetch-слой, типы в `src/api/types.ts`
   строго по §7–8 (руками, TypeScript-зеркало pydantic-моделей).
2. `msw`-моки: 6 сценариев — обычный ответ, ответ с одним `speaker_org`, ответ с
   `организатор-провайдер`, отказ, ошибка `upstream`, долгий ответ (скелетон).
3. Вёрстка сдержанная: инструмент для сотрудника, не лендинг. Тёмная и светлая темы не нужны,
   нужна читаемость длинного русского текста и цитат.
4. Тест: Playwright-сценарий «задал вопрос → увидел ответ → раскрыл источник → отправил фидбек».

## Границы

- Не поднимать бэкенд, не менять контракт. Не хватает поля — эскалировать, не додумывать.
- Не тащить UI-кит целиком ради трёх экранов.

## Готово, когда

`npm run dev` показывает три экрана на моках, Playwright-сценарий проходит, типы совпадают с §7.
