# T-30 — Проверить качество и сравнить четыре подхода

**Статус:** к выполнению. **Зависимости:** T-20 и T-21; вывод в интерфейс — после T-22.
**Результат:** воспроизводимый эксперимент с честными ограничениями, доступный в отчёте и UI.

Порядок работы:

1. На 40–50 вручную размеченных парах «утверждение — фрагмент» проверить судью:
   другая модель и промпт, три прогона, доля совпадений, Cohen's kappa и разброс.
   Разметка — входная работа человека; модель не заменяет её собственными ответами.
   Вход судьи — одно утверждение и один фрагмент; выход — JSON с `verdict`
   (`supported`, `partially`, `not_supported`) и краткой причиной. Судья оценивает
   только наличие опоры, без оценки стиля и полезности.
2. На одинаковых вопросах сравнить: модель без поиска, FTS, выбранный RAG и весь корпус
   в контексте. Использовать существующие `llm/`, `search.py` и `eval/`, без второго конвейера.
3. Зафиксировать настройки и метод до открытия 10 holdout-вопросов. Использовать их только
   в финальной оценке, не подбирать по ним параметры. Повторы для разброса определить заранее.
4. Сохранить сырые прогоны и один `eval/reports/final-comparison.md`: качество, полнота,
   корректные отказы, независимость источников, время, стоимость, удачные и неудачные примеры.
   Recall применим к вариантам с поиском; неприменимые метрики обозначать явно.
5. Заполнить `/api/eval/summary` и существующий `Quality.tsx` этими результатами,
   включая калибровку и ограничения. Экран ничего не пересчитывает через LLM.

Готово, когда:

- Проверен расчёт метрик на примерах с известным ответом; версия корпуса, промпта,
  режима и модель записаны в прогонах. Подтверждённость опубликована только вместе
  с согласием судьи; при отсутствии ручной разметки она обозначена как неизмеренная.
- Весь корпус не выкинут из сравнения. Измерены холодный/тёплый вызовы и фактический кэш:
  текущий CLI игнорирует `cache_system`, поэтому один флаг не считается доказательством кэширования.
- Проверены актуальные доступные модели, тарифы и состав usage. Расчётная стоимость отделена
  от списаний; ни исключение служебных токенов, ни равенство оверхеда между вариантами
  не предполагаются без замера. Для CLI не заявляется управление temperature.
- Вывод допускает отсутствие выигрыша RAG. Малая выборка и неопределённость указаны;
  небольшая разница не объявляется доказанным превосходством.

Без ручной калибровки можно продолжать сбор остальных метрик, но тикет целиком не закрывать.

Найдено при проверке T-32 (14.09.2026): экран «Проверка качества» показывает в колонке
«Вопросов» `n_questions=33` для каждого варианта, а `must_contain_rate` и recall посчитаны
по 10–25 вопросам (разметка и выжившие вызовы). Доля 100% рядом с «33» выглядит сильнее,
чем есть. В `summary.json` нужно отдавать знаменатель каждой метрики и число
несостоявшихся вызовов, а экрану — показывать их рядом с долей.
Контрольный прогон с проверенным prompt caching через API — при доступном ключе;
если его нет и кэш CLI не подтверждён, ограничение стоимостного сравнения оставить явным.
